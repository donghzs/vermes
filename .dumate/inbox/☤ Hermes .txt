四、结论级问题：判定口径混用（这才是重点）

  它自己的 §3 定义「只能 core patch = hook 表达不了」，而它在 §2.1 里给出了 hook 签名（learned_experience_block）—— 说明能表达。随后它用"触碰缓存 invariant + 上游接受概率低"把它降级为 core patch，这是把判据（可表达性）和可行性（上游接受度）混在一个格里。
  正确的三档应该这样落：
    自进化 → 可插件化（静态首轮块走 registered system prompt section；每 N 轮动态块走 pre_llm_call；工具后记录走 post_tool_call），代价是 Vermes 侧改注入载体，不动 core
    记忆织物 → 可插件化（ABC 只强制 4 个方法；分层召回/策展/使用统计是插件内部自由；turn 前召回 = prefetch()、turn 后反思 = sync_turn()）。"17/20 入口无 ABC 对应"是事实，但推不出"需上游开口"
    工作流 → 需上游开口 ✅ 这条它判对了（上游确无 DAG 引擎概念），而这属于发行版化可接受的一档 —— 上游自己的哲学就是 "widen the generic plugin surface"
  → 因此「独立分叉（A）」的决定性理由不成立：发行版化在技术上有路径，成本在"实现改造量 + 上游对新通用 hook 的接受度"，不是"被自进化杀死"。
