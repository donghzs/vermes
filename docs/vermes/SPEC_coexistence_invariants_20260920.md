# SPEC：多引擎并存不变量与验收（本机 macOS）

> 状态：生效中 · 2026-09-20 · 配套脚本 `scripts/check_coexistence.py`
> 适用范围：本机同时运行的 Hermes 官方 / Vermes / QClaw / WorkBuddy / MiMo
> 约束对象：任何一次会改动「安装位置、配置根、端口、解释器、launcher、技能根、引擎代码来源」的改造 —— **尤其是发行版化（引擎层跟随上游）**

## 0. 为什么需要这份 SPEC

用户的核心诉求是：**「Vermes 还是 Vermes，且本机多个引擎能并存」**。

实测事实（2026-09-20）：并存的成立**不依赖"源码不同"**，而依赖**安装层与配置层的隔离**。
Vermes 与 Hermes 官方本来就是同源分叉（1167 个同名文件、Jaccard 0.08–0.14）——"杂糅"早已存在，只是**无规则**。
发行版化要做的，是把这种杂糅从「隐式、无规则」变成「显式、有规则」（引擎=上游、差异全在 `plugins/`）。

因此本 SPEC 的作用是：**把并存从"感觉"变成"每次可验"**。任何改造跑一遍脚本 + 过一遍人工项，即知并存有没有被弄坏。

## 1. 三条禁令（破了这三条，并存必坏）

| # | 禁令 | 为什么 | 破坏后的症状 |
|---|---|---|---|
| 禁1 | **Vermes 不得把引擎装进 / 写进 `~/.hermes/hermes-agent`** | 那是 Hermes 官方的引擎树；上游升级会覆盖、launcher 会撞 | Hermes 升级后 Vermes 起不来；或反向被 Vermes 的文件污染 |
| 禁2 | **不得让 Vermes 共用 `~/.hermes/` 配置根** | 记忆/白名单/密钥作用域会互相污染 | 一个 bot 的配对/白名单/记忆串到另一个；密钥串 profile |
| 禁3 | **不得共用端口与 launchd label** | 两个进程抢同一端口 / launchd 命名空间冲突 | 第二个起不来；或抢端口导致其中一个静默不服务 |

## 2. 九条不变量（脚本逐条验，退出码即结论）

| # | 不变量 | 判据 | 被破坏的后果 |
|---|---|---|---|
| 1 | 进程归属可判定 | 每个运行中引擎进程能唯一归属到一个安装 | 无法定位是谁在占资源/端口 |
| 2 | 配置根隔离 | 各安装配置根互不共用、互不嵌套 | 见禁2 |
| 3 | 状态库隔离 | 每个 `.db` 都在自己配置根内 | 会话/记忆/看板串库 |
| 4 | 端口隔离 | 监听端口归属可判定且无重叠 | 抢端口、静默失去服务 |
| 5 | launchd 命名空间隔离 | `ai.hermes.*`（Hermes）与 Vermes 不重叠 | 服务互相覆盖/无法单独重启 |
| 6 | 解释器/二进制隔离 | 各引擎用自己安装树内的解释器 | 宿主升级/删除 → 被托管方连带故障 |
| 7 | CLI 入口隔离 | `hermes` 与 `vermes` 入口不指向同一文件 | 敲 `vermes` 起了 Hermes |
| 8 | 技能根隔离 | 各 `skills/` 根互不嵌套 | 技能互相覆盖、索引互相污染 |
| 9 | 代码根隔离 | Vermes 源码/装机后端不在 Hermes 引擎树内；装机后端不指向源码树 | 装机随源码漂移；上游升级覆盖 Vermes |

另有两条 ★ 加固检查（本次实跑新增，非原始不变量）：

- **★ 跨安装文件句柄**：A 安装的进程不得持有 B 安装目录下的文件句柄 —— 这是"真隔离"的硬证据（本机实测：通过）。
- **★ 跨安装二进制托管**：A 的解释器在跑 B 的脚本 —— 不是违规，但是**隐性耦合**，宿主升级即连带故障（本机实测：**3 处，见 §4**）。

## 3. 脚本用法（只读）

```bash
python3 scripts/check_coexistence.py            # 默认不变量检查
python3 scripts/check_coexistence.py --deep     # 追加本机网关端口连通性探测
python3 scripts/check_coexistence.py --json     # 机读输出（CI）
python3 scripts/check_coexistence.py --quiet    # 只看 FAIL/WARN
```

- **退出码契约**：`0` = 无 FAIL；`1` = 存在 FAIL（并存已被破坏）→ 可直接接 CI 门禁。
- **只读保证**：仅执行 `ps` / `lsof` / `launchctl` / 路径探测 / 对本机自身端口的 TCP 连接。
  **不发消息、不写文件、不 kill 任何进程**（`--deep` 也只连本机 127.0.0.1 自己的端口）。
- 新增安装（如以后出现新引擎）：在脚本 `INSTALLS` 表加一条（markers / config_root / code_roots / launcher），无需改检查逻辑。

## 3.1 何时跑（接线建议）

| 时机 | 目的 |
|---|---|
| 任何改动安装位置/端口/launcher/配置根之后 | 立即确认并存未破 |
| 打包发布前 | 装机后端指向检查（不变量 9） |
| 上游 canary 流水线里（每日拉上游 main 后） | 确认升级没有连带破坏并存 |
| 发行版化每一刀（自进化 → 上下文引擎 → 记忆织物 → 中文平台）之后 | 逐项验收，失败即回退 |

### 已知 WARN（3 处跨安装二进制托管）与处置建议

| 托管关系 | 性质 | 建议 |
|---|---|---|
| Hermes 的 MCP 服务（2 个进程，pid 48116/53927）跑在 **QClaw 自带的 Python 3.11** 上 | **运行态隐性耦合**：QClaw 升级/删除该解释器，Hermes 的 MCP 即挂 | 把 MCP 启动命令的解释器**钉死到本安装的 venv**（`~/.hermes/hermes-agent/venv/bin/python`）并在该 venv 装齐依赖；否则需显式承认此依赖并写进文档 |
| QClaw 的 node 在跑 Vermes 仓库的 vite dev server（pid 30033） | **开发态**耦合（仅开发时出现，不影响装机） | 可接受；不建议在装机态出现 |

> 另观察（非并存问题，属网关可靠性）：`ai.hermes.gateway` 当前在跑但 `last_exit=75`，说明它至少异常退出过一次后被 launchd 拉起。归 `gateway-reliability` 关注，不计入并存判定。

## 5. 附录：真实消息往返（人工项，脚本不代做）

脚本只能验到"端口可连"，**真实消息往返必须人工**（涉及向外部平台发消息，不自动化）：

1. Hermes 侧：飞书/Telegram 给 Hermes-MAC 发一条，确认回复来自 Hermes（看 `hermes gateway status` 与网关日志）。
2. Vermes 侧：给 Vermes 的渠道发一条，确认回复来自 Vermes。
3. 核对：两条回复**各自来自各自的安装**（互不串台），且两边会话历史分别落在 `~/.hermes/state.db` 与 `~/.vermes/state.db`。

判定：两边各回各的 = 并存端到端成立。

## 6. 与发行版化的关系（本 SPEC 的实际用途）

发行版化的每一刀都要过这份验收：

| 改造项 | 需要重点复验的不变量 | 原因 |
|---|---|---|
| 自进化插件化 | 6（解释器）、★ 句柄 | 注入载体改到 plugins/ 后，进程/句柄归属会变 |
| 上下文引擎跟随上游 | 9（代码根）、4（端口） | 压缩与 web 服务可能换实现与默认端口 |
| 记忆织物 → MemoryProvider | 3（状态库）、★ 句柄 | db 路径解析必须落在自己的配置根 |
| 中文平台 → plugins/platforms | 2（配置根）、6 | 平台插件不得改写 `os.environ`（上游纪律），否则密钥/白名单串 profile |
| 打包/装机 | 9（装机后端不指向源码树） | 防止装机随源码漂移 |
